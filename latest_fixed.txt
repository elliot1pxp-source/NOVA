────────────────────────────────────────────
FIX 1: Retry only applies to EDITED user messages
────────────────────────────────────────────

Problem:
  The client-side retry watchdog (startAttempt) re-sent EVERY failed
  request — including plain new sends and plain assistant regenerations.
  Retrying a plain send could duplicate the user message; retrying a
  plain regeneration re-issued a request against already-truncated state.

v1 (first attempt):
  Added a shared ref retryEligibleUserMessageIdRef, set ONLY by
  handleEditMessage (to the new "::vN" version id) and cleared when a
  generation reached status === "ready".

  BUG in v1 (reported by user):
    The ref was only cleared on status === "ready". If an edit flow's
    generation FAILED (status "error") or was stopped, the stale edited
    message id persisted. The NEXT plain assistant regenerate then:
      a) wrongly armed the watchdog, AND
      b) retried regenerate({ messageId: <stale edited user id> }) —
         regenerating the USER message instead of the assistant message
         the user clicked.

v2 (per-request eligibility — final):
  Removed the shared ref entirely. Retry eligibility is now carried
  PER-REQUEST inside lastOutgoingRef:
      type OutgoingRequest = {
        type: "send" | "regenerate";
        payload: any;
        retryable: boolean;
        editedMessageId?: string;
        retryFn: "sendMessage" | "regenerate";
      };
  - ONLY the edit flow passes retryable: true, via
      startRegenerateWithRetry(undefined, { retryable: true, editedMessageId })
    called DIRECTLY from handleEditMessage (the pendingRegenerateAfterEdit
    state/effect was removed entirely).
  - startSendWithRetry always records retryable: false — plain new sends
    are single-shot; failures surface as an error banner immediately.
  - Plain regenerations (handleRegenerate) also record retryable: false —
    the provider truncates history to the regenerated message, so a
    re-issue after truncation would slice away the old response entirely.
  - The watchdog retry dispatches on retryFn:
      * edit flow (retryFn "sendMessage") → sendMessage() — re-sends the
        LAST user message (the edited version, guaranteed to be last after
        cleanup), no duplicate appended.
      * regen flow (retryFn "regenerate") → regenerate() with NO messageId.
  - The error-suppression effect is gated on
      lastOutgoingRef.current?.retryable && editedMessageId so transient
      errors are hidden only when a legitimate retry is armed.
  - handleStop clears lastOutgoingRef, the timer, and the attempt counter
    so a manual Stop fully cancels the retry system.

FIX 2: "message ...::vN not found" runtime error (retry crash)
────────────────────────────────────────────

Problem (reported by user):
  Runtime error: "message 4Ks4CZhxEciMZBid::v2 not found" at
  ChatView.useCallback[startAttempt] (components/chat-view.tsx:450).
  The retry watchdog was calling regenerate({ messageId: editedMessageId })
  with a USER message id — but AI SDK's regenerate() expects an ASSISTANT
  message id and throws "message not found" for anything else. Worse, after
  a failed regenerate() the SDK may have already TRUNCATED the message out
  of the state, so even an assistant id could be stale.

Fix:
  - The retry re-issues the SAME request type that started the cycle via
    retryFn (see FIX 1): edit flow → sendMessage() (no id), regen flow →
    regenerate() with NO args. After cleanupPartialAssistantMessages the
    last message is the user message the reply belongs to, and
    regenerate() (no args) targets exactly that — never a stale id.

FIX 5: Tree branch model — per-message branch groups
────────────────────────────────────────────

Problem:
  Branches were keyed by the ROOT USER message id and stored full tails
  from the user message. Switching an assistant version could orphan
  downstream messages, and nested assistant branches inside edited user
  branches were impossible to represent.

Fix (unified tree model):
  - BranchGroup = { branches: MessageBranch[], activeIndex,
    parentMessageId } and
    MessageBranch = { messages: UIMessage[], childBranchIds: string[] }.
  - Each EDITED user message or REGENERATED assistant gets its OWN branch
    group keyed by its ORIGINAL message id. Version ids ("::vN") map back
    to the group via branchGroupForMessageRef.
  - Every branch snapshot is a FULL tail from that message:
    [message, assistant reply, ...every downstream message] — children
    stay with their parent version.
  - The useChat messages array IS the active path (kept in sync by every
    handler). computeVisibleMessages is a linear filter (hides system +
    progress-only assistant messages) — no fragile branch substitution,
    because restoring a snapshot would otherwise corrupt the display.
  - branchGroupForMessageRef maps: original ids -> group id, version ids
    -> group id, and each new assistant's id -> its own group.

FIX 6: User message editing — sibling user branches
────────────────────────────────────────────

Problem:
  Editing a user message that was already a version ("::vN") created an
  orphaned group instead of adding a sibling version to the original
  group. Follow-ups sent while a version was displayed could be lost.

Fix (handleEditMessage):
  - Resolve the group via branchGroupForMessageRef[messageId] ?? messageId
    so editing a version adds a sibling to the ORIGINAL group.
  - REFRESH the current (leaving) version's branch with the full tail
    from this message BEFORE truncating — follow-ups sent while this
    version was displayed stay inside its snapshot.
  - Add the new "::vN" version ({ messages: [editedMessage] }), switch the
    group to it, truncate the visible tail, then trigger the edit
    regeneration with retryable: true.
  - The original conversation branch remains fully available via the
    switcher.

────────────────────────────────────────────
FIX 7: Assistant retry — sibling assistant branches (not children)
────────────────────────────────────────────

Problem:
  Retrying an assistant could be treated as a continuation (child) instead
  of an alternative version (sibling), and the old assistant's downstream
  was not preserved.

Fix (handleRegenerate + onFinish):
  - handleRegenerate resolves the group via branchGroupForMessageRef
    (assistant may already be a version), refreshes the leaving branch's
    tail (assistant + downstream), sets regeneratingAssistantIdRef, then
    calls startRegenerateWithRetry({ messageId }).
  - onFinish regeneration path: the SDK has TRUNCATED the old assistant
    from messages — find the NEW assistant at the end, push
    messages.slice(newAssistantIdx) as a NEW BRANCH VERSION (sibling,
    same parent), set activeIndex to it, and map the new head id to the
    group. The original response remains accessible as version 1.
  - The switcher counter shows < 1/2 > / < 2/2 >.

────────────────────────────────────────────
FIX 8: Nested assistant branches inside edited user branches
────────────────────────────────────────────

Problem:
  Assistant retries inside an edited user branch could escape their user
  version and appear under another user version.

Fix:
  Because each message owns its group (FIX 5), an assistant retry inside
  an edited user branch is scoped to that assistant's group, which lives
  inside the user version's branch snapshot. Switching user versions swaps
  the whole subtree — nested assistant groups come along, and handleBranchNav
  syncs nested group activeIndexes so their counters match the displayed
  version. Assistant retries can never leak across user versions.

────────────────────────────────────────────
FIX 9: Branch switching — only switch the selected node, load its child chain
────────────────────────────────────────────

Problem:
  Switching between assistant versions could keep or remove messages below
  the node incorrectly, mixing children from different versions.

Fix (handleBranchNav):
  - Save the leaving branch as messages.slice(msgIdx) — the full visible
    tail from the clicked message (its child chain).
  - Load the selected branch's messages and splice them in from the same
    index.
  - Sync NESTED branch groups: for every message in the restored snapshot
    that is a group head, set that group's activeIndex to the version
    present in the snapshot — the switcher counter always matches the
    displayed version, never mixes versions.
  - Swapped-in messages are added to noAnimateIdsRef (flat render, no
    entrance animation).

────────────────────────────────────────────
FIX 10: Follow-ups extend the correct branch (edited-version ancestor)
────────────────────────────────────────────

Problem:
  Sending a follow-up after a response inside an EDITED user version only
  checked the last user message's group (which usually doesn't exist), so
  the ancestor user group's active branch was NOT extended — switching
  away and back lost the follow-up.

Fix (onFinish normal path):
  Walk EVERY message in the current array; for each message that is the
  ACTIVE HEAD of a group (i.e. the version currently displayed), extend
  that group's active branch with messages.slice(i). This covers:
    - user groups whose root sits ABOVE the last user message (edited
      versions),
    - assistant groups,
    - nested groups at any depth.
  Then ensure the freshly streamed assistant has a branch group so it can
  be regenerated later as a sibling (same parent).

Problem (reported by user):

     appeared on the USER message row.
  B. After editing a USER message, the switcher ALSO appeared on the
     assistant reply.

      lone "1 / 1").

FIX 14: Background generation when switching chats
────────────────────────────────────────────

Problem (reported by user):
  Switching to another chat (or creating a new chat) while an assistant
  response was still generating INTERRUPTED/CANCELLED the generation.
  ChatView was mounted with key={currentChatId}, so switching chats
  UNMOUNTED the old ChatView — killing its useChat state, the in-flight
  stream, the retry watchdog timers, and losing the response.

Requirements:
  - Switching chats must NOT cancel active assistant generations.
  - Creating a new chat must NOT cancel existing generations.
  - Each chat maintains its own independent generation state.
  - Multiple chats can generate simultaneously (like browser tabs).
  - Generation stops ONLY on: manual Stop, request failure, page close,
    or explicit cancellation — never on a chat switch.
  - Generation state lives OUTSIDE the active view; the active view only
    controls DISPLAY.

Fix (app/page.tsx + components/chat-view.tsx):
  - app/page.tsx no longer remounts ChatView per chat. Instead it keeps
    EVERY chat's ChatView MOUNTED, wrapped in a div that is hidden
    (className "hidden") unless it is the active chat:
        <div className={cn("h-full w-full", chatId === currentChatId ? "" : "hidden")}>
          <ChatView chatId={chatId} isActive={chatId === currentChatId} ... />
        </div>
    Switching chats now only toggles CSS display — the mounted ChatView
    (and its useChat stream, retry timers, branch state) keeps running.
  - mountedChatIds is a memo of chat ids to mount: all chats in `chats`
    plus the pending (new) chat id when activeChatId === null. The
    pending chat's id is now STATE (pendingChatId) kept in sync with a
    ref, so "New Chat" always re-renders and mounts a fresh empty view.
  - The pending chat → real chat transition is seamless: onFirstMessage
    adds the chat to `chats` under the SAME id the pending view was keyed
    by, so the key stays stable and the view never remounts.
  - ChatView gains an isActive prop. When a hidden chat becomes active
    again, a new effect restores scroll position: if a generation was in
    flight (status submitted/streaming) OR the user was following the
    bottom when they left, it scrolls to the bottom so a completed
    background response is visible; otherwise the scroll position is left
    untouched (no yanking the user up/down). It remembers the follow
    state via wasFollowingWhenHiddenRef.
  - Deleting a chat still cancels its generation (the id leaves
    mountedChatIds → view unmounts), which is correct — deletion is an
    explicit cancellation.

Result:
  - Chat A can keep generating while the user switches to Chat B and
    sends messages there, then return to Chat A to find the completed
    (or still-streaming) response — exactly like changing tabs.
  - Multiple chats can have independent active generations simultaneously.

FIX 15: New empty chat restoration after page refresh
────────────────────────────────────────────

Problem (reported by user):
  Steps to reproduce:
  1. Open an existing chat.
  2. Create a new chat.
  3. Do not send any messages.
  4. Refresh the page.
  5. The app returns to the previous chat instead of staying on the
     newly created empty chat.

Root Cause (two issues):
  A) Hidden background ChatViews (kept mounted so their generations keep
     running) fire the onFirstMessage effect on mount — they load their
     existing messages from localStorage, and the effect fires whenever
     messages.length >= 1. onFirstMessage calls handleFirstMessage, which
     sets activeChatId to THAT chat and updates the URL — yanking the user
     out of their current (new/empty) chat back to the previous one.

  B) The pending (new, empty) chat id was never persisted. handleNewChat
     only stored it in a ref/state; on refresh a brand-new random id was
     generated, so the empty chat the user was on was lost.

Fix:
  A) components/chat-view.tsx — the onFirstMessage effect is now gated on
     isActive: only the chat currently being DISPLAYED may fire it. Hidden
     background chats no longer re-navigate.

  B) app/page.tsx — the active chat id is persisted IMMEDIATELY via
     saveLastChatId() in every navigation path:
       - handleNewChat: saves the new pending chat id
       - handleSelectChat: saves the selected chat id
       - handleFirstMessage: saves the chat id
       - handleDeleteChat / handleDeleteAllChats: saves the fresh pending id
     On hydration, the URL chat id wins; otherwise loadLastChatId() is
     restored — if it exists in the chat list it becomes the active chat
     (even with zero messages), and if it does NOT exist (a fresh empty
     chat that never received a message) it is restored as the pending
     chat id. The app never falls back to an older chat just because the
     current one has no messages.

Behavior after fix:
  - Create a new chat → refresh → the SAME empty chat is restored (URL "/",
    empty message list, previous chats still in the sidebar).
  - Sending the first message in the restored empty chat converts it into
    a real chat under the SAME id (URL /chat/{id}, appears in sidebar).
  - Only switches away from the active chat if: the id no longer exists,
    the user manually selects another chat, or the chat was deleted.

FIX 17: DeepThink uses the model's NATIVE reasoning (no separate planner)
────────────────────────────────────────────

Problem:
  DeepThink ran a separate "Planner Agent" sub-call (`MODELS.deepthink`)
  that produced a structured "handoff plan", injected it into the system
  prompt as "Deepthink guide response:", then the main model answered.
  That cost an extra model call and duplicated tokens, and the planner's
  plan could diverge from the responder's actual reasoning.

Fix (app/api/chat/route.ts + lib/llm-providers.ts):
  - REMOVED the planner sub-call, the `Deepthink guide response:` prompt
    injection, and the `deepthink` key from `MODELS` / `PRIMARY_MODELS` /
    `FALLBACK_MODELS` entirely.
  - DeepThink now sends the chat model's OWN native reasoning: the top-level
    `reasoning` option maps to `reasoning_effort` on the wire (both
    endpoints advertise effort tiers none/low/medium/high/xhigh).
  - The AI SDK's chat-completions parser DISCARDS `reasoning_content`
    (verified: not in its chunk schema), so `createProviderClients(apiKey,
    { onReasoningDelta })` tees the raw SSE response body through a
    TransformStream and extracts `choices[0].delta.reasoning_content`.
    The tee is enabled ONLY on a second client set (`responseClients`)
    created for the final response when deepThink is on — sub-calls never
    flood the thought block.
  - `streamTextWithFallback` gained `onFirstText` (fires once before the
    first answer text-delta): the route flips `data-thought` from
    "thinking" to "done" at the exact moment the answer starts, so the
    thought block shows "Thought for Ns".
  - Thought block now streams the model's LIVE reasoning text (throttled
    150ms) instead of waiting for the full planner plan.
  - Fetch wrappers (`createCustomFetch` / `createReasoningTeeFetch`) now
    set `duplex: "half"` (Node undici requirement when re-sending a
    streamed request body). This fixed two runtime errors found during
    the rewrite:
      a) "RequestInit: duplex option is required when sending a body."
      b) "Invalid state: The ReadableStream is locked" — the tee must use
         `pipeThrough` WITHOUT a manual `getReader()` (pipeThrough reads
         the source itself; getReader locks the stream first).
  - `onAttemptStart` resets the reasoning accumulator so a failed attempt
    switched to the other endpoint never leaks stale thinking text.

FIX 18: Reasoning level selector + reasoning never enabled accidentally
────────────────────────────────────────────

Problem:
  There was no way to pick reasoning strength, and the endpoints reason BY
  DEFAULT even when no reasoning parameter is sent — so web search / file
  analysis sub-calls and plain chat (DeepThink off) all burned hidden
  reasoning tokens.

Fix (components/chat-input.tsx, components/chat-view.tsx,
      app/api/chat/route.ts, app/api/summarize/route.ts):
  - UI: the DeepThink pill is the master toggle. When ON, a
    Low / Medium / High segmented selector appears (default Medium); when
    OFF, no reasoning options are shown at all. The chosen level rides in
    the request body as `reasoningLevel`.
  - Server (chat route): `resolvedReasoning = deepThink ? (validated level
    ?? "medium") : "none"`. "none" is sent EXPLICITLY because these
    endpoints think by default — sending nothing would leave hidden
    reasoning running (verified: a bare "say hi" consumed 26+ reasoning
    tokens; `reasoning_effort: "none"` used 2).
  - Web-search query generation, file analysis, and summarization
    sub-calls ALWAYS send `reasoning: "none"` — they are utility calls and
    must never reason.
  - The route logs `[chat] reasoning: none|low|medium|high` per request.
  - Verified at the wire level via fetch interception:
      reasoning "none"  -> reasoning_effort "none"
      reasoning "low"   -> reasoning_effort "low"
      reasoning "high"  -> reasoning_effort "high"

FIX 19: "Extra High" (xhigh) reasoning level + paid-tier gating
────────────────────────────────────────────

Problem:
  The endpoints advertise effort tiers up to "xhigh", but the UI only
  offered low/medium/high. High and xhigh are expensive (long thinking
  phases) and should be a paid-tier perk — free users must not be able to
  select them, and the server must not honor them even if a client sends
  them anyway.

Fix (components/chat-input.tsx, components/chat-view.tsx,
      app/api/chat/route.ts):
  - UI (chat-input.tsx): `ReasoningLevel` is now
    "low" | "medium" | "high" | "xhigh"; `REASONING_LEVEL_LABELS` maps
    xhigh → "Extra High". The selector renders Low / Medium / High /
    Extra High. High and Extra High are DISABLED for free users
    (`isRestricted = (level === "high" || level === "xhigh") && !isPaidUser`)
    — greyed out, `cursor-not-allowed`, `aria-disabled`, with a
    "Requires paid tier" tooltip; clicking does nothing.
  - chat-view.tsx passes `isPaidUser={hasPaidAccess}` to both ChatInput
    instances (hasPaidAccess = paid server mode + unexpired code).
  - Server (chat route): the paid-code lookup (`hasPaidAccess`) was moved
    BEFORE the reasoning resolution. `isRestrictedLevel` = high or xhigh;
    if a free user requests one, it silently falls back to
    `DEFAULT_REASONING_LEVEL` ("medium") — the server never honors a
    restricted level without a valid paid code, even from a tampered
    client.
  - `REASONING_LEVELS = ["low", "medium", "high", "xhigh"]`; the route
    logs `[chat] reasoning: none|low|medium|high|xhigh` per request.
  - Verified: free-user requests for "high" and "xhigh" both log
    `reasoning: medium`; paid requests pass the level through.

Summary of behavior after all fixes
────────────────────────────────────────────

Regenerating an assistant message:
  1. Old response + its downstream are saved as branch version 1
  2. New response streams in as a NEW sibling version (same parent)
  3. Raw < n / m > switcher appears ONLY on the assistant rows
  4. Switching restores the exact child chain of the selected version
  5. Downstream messages of sibling versions are never mixed

Editing a user message:
  1. Original message + its subtree are saved as branch version 1
  2. Edited version (::vN) + its own assistant responses become a sibling
  3. Raw < n / m > switcher appears ONLY on the edited user message
  4. Nested assistant retries stay inside that user version
  5. Follow-ups sent after the edited version extend ITS branch

Retry behavior:
  1. Auto-retry fires ONLY for the edited-user-message flow
  2. Plain sends and plain assistant regenerations fail fast with an
     error banner — never silently re-requested
  3. A retry re-issues the same request type (sendMessage for edits,
     regenerate with no args for regens) — no "message not found" crash

Bubble sizing:
  1. User bubbles are content-fit (w-fit), capped at 70% width
  2. Short messages stay compact; long messages wrap naturally
  3. Assistant prose uses the full available width, no empty bubble

Background generation:
  1. Switching chats / creating a new chat NEVER cancels an in-flight
     generation — every chat's ChatView stays mounted (hidden when not
     active), so its stream, retry timers, and branch state keep running
  2. Returning to a chat shows the completed (or still-streaming) response
  3. Generations stop only on: manual Stop, request failure, page close,
     or explicit cancellation (deleting the chat)

Empty chat restoration:
  1. A new empty chat's id is persisted immediately (saveLastChatId) and
     restored on refresh — the SAME empty chat is kept, never an older one
  2. The active chat id is never derived from message existence — a chat
     with zero messages is still a valid, restorable chat

Native DeepThink / reasoning:
  1. DeepThink ON → the main chat model thinks natively at the chosen
     level (low/medium/high/xhigh), and its LIVE reasoning text streams
     into the Thought block, ending with "Thought for Ns"
  2. DeepThink OFF → explicit reasoning_effort "none" is sent — no hidden
     thinking, no wasted reasoning tokens
  3. Web search, file analysis, and summarization NEVER reason
  4. The reasoning-level selector appears only while DeepThink is ON
  5. High and Extra High are paid-tier only — disabled in the UI for free
     users, and the server silently downgrades them to medium if a free
     client sends them anyway

No duplicate key errors, no disappearing messages, no orphaned branches,
no stale retry markers, no crashes, no oversized bubbles, no lost
generations, no lost empty chats, no invisible input textarea, no hidden
reasoning, no planner round-trip, no free-tier access to high/xhigh.

FIX 24: Web search — Serper Scrape API for top 3 page contents

  `searchWithPageContent` fetched every result page itself with raw

How the API works (per user requirements):
  - POST https://scrape.serper.dev
  - Headers: X-API-KEY (Serper key), Content-Type: application/json
  - Body: { url, includeMarkdown? } — the service fetches the page,
    extracts the main content, returns { text, markdown, metadata, jsonld }.

    results with URLs in parallel and returns merged results

  - `searchWithPageContent(query, serperApiKey?)` — when a Serper key is
    available, the top 3 results get content from the Scrape API and

    ALL results use the raw HTML fetch (previous behavior).
  - The manual GET /api/search route is unchanged (no page fetch).

  - No extra cost when no SERPER_API_KEY is configured, and no regression

FIX 25: Streaming freeze + "Maximum update depth exceeded" on long output
────────────────────────────────────────────

Problem (reported by user):
  With a LOT of output in one message, the site freezes while streaming
  ("when streaming became very long context, the site freezes"), and
  intermittently crashes mid-think or mid-respond with:
    "Maximum update depth exceeded. This can happen when a component
     repeatedly calls setState inside componentWillUpdate or
     componentDidUpdate. React limits the number of nested updates to
     prevent infinite loops."

Root Cause (both symptoms share ONE root cause):
  1. react-markdown v10 does NOT memoize. `${ReactMarkdown}` re-ran a full
     micromark parse + element build on EVERY render. With useChat's
     200ms throttle and a 50k-char streaming message, that meant the whole
     document was re-parsed ~5x/sec — saturating the main thread →
     FREEZE.
  2. Simultaneously, `StreamingMarkdown`'s `useLayoutEffect` ran on every
     text change: walked the ENTIRE DOM with a TreeWalker, called
     `getBoundingClientRect` (forces layout), then `setCursorPosition`
     synchronously in the layout phase. Combined with the SDK's throttled
     `replaceMessage → structuredClone` store writes, this class of
     render-phase setState on huge trees is exactly what trips React's
     "Maximum update depth exceeded" guard (the crash is surfaced into
     useChat's `error` state by the SDK's stream-catch handler, so it
     renders in the error banner).
  3. The messages-watcher effect recomputed an activity key by
     `JSON.stringify`-ing EVERY part of the last assistant message on
     every `messages` change — another O(n) cost per chunk.

Fix (components/chat-message.tsx, components/chat-view.tsx):

  Incremental markdown committing (chat-message.tsx):
    - New `SettledMarkdown` component: a `React.memo` wrapper around
      `ReactMarkdown`. Because memo compares the `text` prop, the settled
      prefix is only re-parsed (a full micromark run) when the committed
      length actually advances — NOT on every stream token.
    - `StreamingMarkdown` now splits the message into:
        * a SETTLED prefix (`text.slice(0, committedLen)`) rendered by
          `SettledMarkdown` (memoized markdown), and
        * a streaming TAIL (`text.slice(committedLen)`) rendered as cheap
          plain text with an INLINE pulsing cursor — no DOM tree-walk, no
          layout measurement, no `useLayoutEffect`.
    - The commit loop runs in `useEffect` (after paint, so a heavy re-parse
      never blocks painting) and advances `committedLen` in chunks of
      `MARKDOWN_COMMIT_CHUNK = 1600` chars, snapping to the previous
      newline so markdown blocks (lists/code fences) aren't cut mid-block.
      It skips negligible growth below `MARKDOWN_COMMIT_MIN = 300`.
    - When the stream ends (`isStreaming` false), it commits the full text
      in one final markdown render.
    - The same incremental pattern is applied to `ThoughtBlock`'s
      streaming thought text (previously re-parsed as markdown every
      150ms delta during long DeepThink phases).

  Cheap activity key (chat-view.tsx):
    - The retry-watchdog watcher no longer JSON.stringify's the whole
      message. It now builds an O(1) fingerprint from the last text part's
      length + a 64-char tail + part count — enough to detect "content
      changed" without copying tens of thousands of chars per stream chunk.

  Removed the dangerous measurement entirely:
    - The old absolute-positioned cursor (`cursorPosition` state + TreeWalker
      + getBoundingClientRect in useLayoutEffect) is gone. The tail now
      renders the cursor as an inline block right after the plain text.

Result (verified live):
  - A ~90k-char DeepThink response streamed with NO "Maximum update depth"
    error and no error banner.
  - A responsiveness probe (requestAnimationFrame) over ~6,300 frames
    during streaming showed only 6 short stalls (>200ms, mostly ~250ms
    during 1600-char commits) vs a hard freeze before — the page stayed
    interactive while streaming.
  - The settled markdown fully committed after the stream (headings,
    tables, code blocks all rendered; zero leftover tail spans).
  - Typecheck passes.
